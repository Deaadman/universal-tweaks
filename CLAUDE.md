# CLAUDE.md

Guidance for Claude Code on this repo — a MelonLoader mod for The Long Dark. Swap placeholders (mod name, deps) when reusing for similar projects.

## Project
- MelonLoader mod for The Long Dark, built against IL2Cpp-stripped assemblies.
- Patches game behavior via Harmony (`HarmonyLib`), not by editing game code.
- Ships as a single `.dll` in the game's `Mods` folder — some mods instead ship as a `.zip` bundling the `.dll` with a Unity asset bundle/package; check for a `UnityAssets/` or similar folder and a packaging step before assuming single-DLL output.

## Layout
- `Source/<ModName>.csproj` — main net6.0 project.
- `Mod.cs` — MelonMod entry point.
- `BuildInfo.g.cs` — **generated by MSBuild, never hand-edit**. Change `.csproj` (`Product`, `Authors`, `VersionPrefix`) instead.
- `Properties/Settings.cs` — all user-facing config; check it before assuming a feature doesn't exist.
- `Properties/AssemblyInfo.cs` — MelonInfo/MelonGame/MelonIncompatibleAssemblies attrs.
- `Resources/` — embedded assets, localization json.
- `Dependencies/` — local DLLs not on NuGet.

## Build
- `net6.0`, `TreatWarningsAsErrors` on — warnings fail the build.
- MelonLoader version is pinned (currently 0.7.2) — check `AssemblyInfo.cs`/`BuildInfo.g.cs` for current value; don't bump incidentally.
- `Nullable` enabled — respect it, don't just add `!`.
- Global usings are centralized in `.csproj` — don't re-add them per file.
- Local-only deps go in `Dependencies/*.dll` with hint path, not `dotnet add package`.
- If a `CopyToModsFolder` target exists, it's machine-specific and disabled by default — leave it alone. Not every project has one.
- If a `WriteVersion` target exists, it writes `Version.txt` for CI to read — don't rename/remove without updating the workflow. Check the actual release workflow for how it sources the version rather than assuming this mechanism.

## Harmony Patches
- Prefer `Postfix` over `Prefix` unless you need to block/replace original behavior.
- Patch targets live in `Il2Cpp` namespace (interop stubs, not real source).
- Check for existing workarounds before assuming standard .NET works (e.g. IL2Cpp span/stream quirks).
- Read `Settings.Instance.<Field>` live inside patches — don't cache at startup (settings can change in-game).
- The patched-class instance parameter must always be named `__instance` — never `instance`. This is a hard requirement, not a style preference; Harmony resolves it by exact parameter name.

## Settings.cs
- Not every mod has one — some are non-configurable (no in-game options menu at all). Check `Properties/Settings.cs` exists before assuming this section applies.
- New options need `[Name(...)]`/`[Description(...)]`; numeric → `[Slider(...)]`; enums → `[Choice(...)]`.
- Group new fields under matching `#region`/`[Section(...)]`; new region only for genuinely new feature.
- Conditional visibility → wire into `RefreshFields()` via `SetFieldVisible`.
- `OnConfirm()` pushes settings into already-live game objects — hook here if a tweak must affect the current save/scene without restart.

## Logging
- Use **ComplexLogger**, not `MelonLogger`/`Melon<Mod>.Logger` directly, and not a bespoke wrapper — this is the standard across these projects going forward.
- If a project has an existing custom logging wrapper (e.g. a `Logging.cs` around `Melon<Mod>.Logger`), treat it as legacy to migrate off of, not a pattern to copy into new code. Check what the project currently uses before assuming ComplexLogger is already wired up.
- Wrap resource/reflection-heavy code (embedded resources, asset bundle loads, reflection) in try/catch with error logging.

## Localization
- Not every mod is localized — check for a `Resources/Localization.json` (or similar) and a localization library reference before assuming this section applies.
- Where localization is active, user-facing strings go through that file rather than being hardcoded in `Settings.cs` attributes or patch code.

## Testing
- xUnit, only for pure engine-decoupled logic (no `Il2Cpp`/`UnityEngine`/`MelonLoader` types).
- Don't test Harmony patches directly — extract pure logic into helpers if needed.
- Convention: sibling `Tests/<ModName>.Tests/` project, referencing main project, excluded from mod build.
- Not present in every project — check for `*.Tests.csproj` before assuming one exists.

## Linting
- `dotnet format`, enforcing `.editorconfig` — no extra analyzers needed.
- CI should run `dotnet format --verify-no-changes`.
- Run locally before committing.

## Commits
- Never list Claude (or any AI) as a co-author/commit partner — no `Co-authored-by` trailer, no attribution footer.
- Keep commit messages short and concise — a single summary line is preferred; only add a body if genuinely necessary.
- Reference related issue numbers when applicable (e.g. `#21`).
- Work happens as direct commits on `develop` (no per-change PRs) — a single PR merges `develop` into `main` when cutting a release. Release notes are therefore generated from **commit messages**, not PR titles/labels — see Changelog below for the convention that depends on.

## Changelog
- If `cliff.toml` exists at the repo root, release notes are auto-generated from commit messages via [git-cliff](https://git-cliff.org/) — check for it before assuming notes are hand-written.
- **Write the commit subject as the actual changelog line**, starting with the category as a natural leading verb — no colon/prefix needed:
  - `Added ...` / `Adding ...` → **Added**
  - `Changed ...` / `Updated ...` / `Adjusted ...` / `Improved ...` → **Changed**
  - `Deprecated ...` → **Deprecated**
  - `Removed ...` → **Removed**
  - `Fixed ...` → **Fixed**
  - `Secured ...` / `Patched ...` → **Security**
  - Anything else (`chore:`, `ci:`, `test:`, `docs:`, `refactor:`, `build:`, `internal:`, merge commits, dependency bumps) is dropped from the generated notes entirely — this is how internal-only work (e.g. adding unit tests) stays out of player-facing release notes.
- Write the sentence as something a player should actually read — it's rendered verbatim, unedited, as the bullet point (e.g. `Fixed the fatigue penalty not applying to both stews`, not `fix: stew bug`).
- The rolling `nightly` prerelease tag is explicitly excluded from version-boundary detection (`skip_tags` in `cliff.toml`) — nightly notes accumulate everything since the last **stable** tag, not just since the last nightly build, and reset only when a real version is tagged.

## CI / Release
- Look for a nightly-release workflow under `.github/workflows/` (commonly `release_nightly.yml`): builds on push to `develop`, tags a rolling `nightly` prerelease, uploads the DLL, and generates categorized notes via git-cliff (see Changelog). Filename/trigger branch may differ per project — check the actual workflow rather than assuming this exact name.
- A stable release is triggered by pushing a `vX.Y.Z` tag to `main` (after the `develop → main` PR merges) — look for a tag-triggered `release.yml` before assuming this is still a manual process. It verifies the tag matches `VersionPrefix` in the `.csproj` before building, then generates notes via git-cliff for just that tag's commits.
- Required order: lint → tests → build → publish. A lint/test failure must hard-stop before publishing.
- Version comes from `VersionPrefix` in `.csproj` — bump there (to match the tag you're about to push), not in workflows.

## Compatibility
- Declare `[assembly: MelonIncompatibleAssemblies(...)]` for overlapping mods; update README's "Incompatible Mods".
- Required deps (NuGet or local DLL) — keep README's "Required Dependencies" in sync.

## Documentation & Comments
- XML doc comments (`/// <summary>`): only where a method/property's name and signature don't already convey behavior, constraints, or gotchas (e.g. "must be called before `OnInitializeMelon`", "returns null on IL2Cpp marshalling failure") — not a blanket requirement on every member.
- Skip XML docs on trivial one-line Harmony `Prefix`/`Postfix` methods and other self-evident internals; this is a mod DLL, not a published library.
- `Settings.cs` fields are already self-documenting via `[Name(...)]`/`[Description(...)]` — don't duplicate that into XML docs too.
- Inline comments: default to none — clear naming carries the "what". Add one only for the "why" (an IL2Cpp/MelonLoader-specific workaround, a non-obvious ordering/timing requirement, a magic number tied to game balance, or something that would genuinely surprise a future reader).
- Keep inline comments to a single short line — no multi-paragraph blocks, and don't narrate the current task/PR/issue (that belongs in the commit message).

## Conventions
- `.editorconfig`: 4-space indent, 120 col, sorted usings — enforced via `dotnet format`.
- Feature/patch classes: `internal` by default.
- No defensive null-checks/error handling for game states that can't occur — match the existing terse style.
